# Shared evidence brief for the issue drafts

Source of every finding: the `benchmarks/operator-sim` harness in this repo (branch `bench/operator-sim`), run 2026-11-10/11.
Issue drafts in this folder must be understandable without this brief, so copy the facts you need into each issue.

## Test environment

- kind v0.33.0, Kubernetes v1.37.0, 1 control plane + 6 workers (3 fake zones), single 16 vCPU / 62 GiB host.
- valkey-operator v0.8.0 (Helm chart `valkey/valkey-operator` 0.8.0). `ValkeyCluster` `bz`: 12 shards × (1 primary + 2 replicas) = 36 pods, no persistence, `maxmemory 256mb`, `allkeys-lru`, `slowlog-log-slower-than 10000`, `latency-monitor-threshold 10`, `cluster-slot-stats-enabled yes`.
- Valkey 9.1.2, rolled to 9.1.3 by the rollingUpdate phase.
- BetterDB Monitor v0.55.0 (image `betterdb/monitor:0.55.0-no-ai`) and, for the full runs, a build of branch `fix/anomaly-cumulative-counter-deltas` (commit 173a4a3f, on master ee9d1735). Helm chart `betterdb/betterdb-monitor` 0.51.1 with the image tag overridden. `STORAGE_TYPE=postgres`, `CLUSTER_AUTO_REGISTER_NODES=true`, `ANOMALY_POLL_INTERVAL_MS=1000`, `WORKSPACE_DISABLED=true`, Enterprise license.
- Seed connection = the operator's headless Service `valkey-bz.valkey.svc.cluster.local:6379`; 36 auto-registered child connections (one per pod), connected as a minimal-ACL user (docs/minimum-acl.md read-only line).
- Load: GLIDE app generator 3000 rps (HGET/INCR/INCRBY+EXPIRE/SADD+SISMEMBER/ZADD+ZRANGE), memtier ~1.5k req/s; 1M keys preloaded.
- Ground truth: an independent per-node sampler (raw RESP, one socket per node): INFO every 1 s on primaries / 5 s on replicas, CLUSTER NODES summary every 5 s per node, SLOWLOG/COMMANDLOG deltas (primaries only), CLUSTER SHARDS every 5 s.
- Scenario: 6-min baseline, then spike (3× app RPS), hotShard, slowCommands (SMEMBERS on a 1M-member set, 40 calls / 90 s = one every 2.25 s), memoryPressure (CONFIG SET maxmemory 64mb + new-key flood), replicaLag (Chaos Mesh 200 ms + 1 mbps primary→replica), primaryKill (graceful pod delete), rollingUpdate (operator image roll).

## Findings (numbers verified against the run data)

1. **Lifetime counters scored as gauges.** v0.55.0 `proprietary/anomaly-detection/anomaly.service.ts` `initializeMetricExtractors` fed raw `keyspace_misses`, `evicted_keys`, `acl_access_denied_auth` to z-score detectors. Steady uninjected load: 53 `keyspace_misses` events in 5 min, e.g. "CRITICAL: keyspace_misses spike detected. Value: 33.20K, Baseline: 33.04K (0.5% above normal, Z-score: 3.39)". Fixed on branch `fix/anomaly-cumulative-counter-deltas` (173a4a3f, unpushed): per-second rate, first sample/reset skipped, cleanup on connection removal, tests. After the fix: "keyspace_misses … Value: 2.10K/s, Baseline: 17/s".
2. **Slowlog detector alerts on BetterDB's own polling.** Final run: all 315 out-of-window findings fell in the 6-min warm-up; 78 were slowlog (slowlog_last_id 73 + slow_queries groups 5), in waves ~60 s apart on many nodes at once, each "Value: 1, Baseline: 0 (…% above normal) → CRITICAL". On primaries (where the sampler reads SLOWLOG), 12 of 17 warm-up entries were BetterDB's own commands: client names `BetterDB-Monitor` and `BetterDB-Monitor-Node-<id>`, commands `CLUSTER SLOT-STATS`, `CLUSTER NODES`, `CLUSTER SHARDS`, `LATENCY HISTOGRAM`, 10–45 ms. Previous run: 7 of 9. Slowlog detector = per-poll delta of slowlog last id (v0.55.0 anomaly.service.ts ~1530–1560) into a z-score detector.
3. **No floor on near-constant / near-zero baselines.** `fragmentation_ratio` CRITICAL for 1.01 → 1.02 ("1.0% above normal, Z-score: 7.68"); `cpu_utilization` WARNING "Value: 2, Baseline: 2 (44.4% above normal)"; slowlog "Value: 1, Baseline: 0 → CRITICAL". `spike-detector.ts`: `consecutiveRequired` default 3 (line ~45).
4. **Warm-up storm on fresh deploy.** BetterDB deployed onto an idle cluster 5.5 min before load: 237 non-slowlog findings across all 37 connections, 176 of them in a single minute as load started (cpu_utilization 48, fragmentation_ratio 37, memory_used 37, input_kbps 35, ops_per_sec 32, connections 24, groups …). 0 findings outside fault windows in the 34 min after warm-up. Detector warm-up = 30 samples, rolling window 300 samples (`metric-buffer.ts`), cooldown 60 s.
5. **Global Anomalies page dominated by monitoring commands.** Top of `/anomalies` (seed connection) = "P99 latency regression detected — Sustained P99 latency degradation: cluster|shards p99 2.1ms (baseline 0.5ms, 4.6x)" and `cluster|nodes` cards (command_p99 / latency-regression, from INFO latencystats). These are commands BetterDB and the harness issue.
6. **No finding for "primary with zero attached replicas".** During every operator roll (4 of 4 scenario rolls), 12/12 shards' primary had `connected_slaves:0` for 6–37 s (1 s sampling). Mechanism: operator restarts replica #2 before replica #1 has rejoined; the restarted pod reports `role:master` (empty) until re-joined; Kubernetes marks it Ready. BetterDB raised failover/role findings but nothing for this state. Operator issue valkey-io/valkey-operator#563 (fix PR #562 unmerged).
7. **Stale role view ("ghost slotless master") displayed, not flagged.** After a failover/roll, part of the cluster keeps listing the demoted primary as `master` with no slots while the node reports `role:slave` and replicates. 3 of 4 scenario rolls; 1 of 3 rolls in the clean kubectl-only repro (no BetterDB, no load). Clean repro: 7/36 nodes held node 6758063… at config epoch 146 as `master`; the node's own `CLUSTER NODES` line: `myself,slave … 145` — config epoch went backwards across pod replacement. BetterDB Cluster page: "Monitoring 13 master nodes and 23 replicas" for a 12×2 cluster. v0.55.0 has `proprietary/anomaly-detection/ghost-membership-detector.ts` (dead node-id at an endpoint) — doesn't cover this. Persists 5–10 min (until observation ended).
8. **Planned operator rolls page like incidents.** Each role change in a roll raises `replication_role` CRITICAL ("Node role changed from master to replica — possible failover or split-brain") and `node_failover` groups. No maintenance window / silence / roll-aware suppression in v0.55.0; `PATCH /api/settings/anomaly/detectors` only changes thresholds. The operator exposes roll state: ValkeyCluster `.status.state/reason` (`Reconciling`/`UpdatingNodes`), `.metadata.generation` vs `.status.observedGeneration`, ValkeyNode `.spec.workloadRevision`.
9. **Per-connection duplication during a roll.** First full run's 36-pod roll: 676 `cluster_topology` events in ~10 min across 37 connections (each connection reports the same cluster-wide change).
10. **Per-node history breaks on IP change.** Auto-registered child connections are keyed by the address in CLUSTER NODES (pod IP). Every roll/kill gives pods new IPs → old children retired, new ones registered with new ids; per-node anomaly history stays on the retired id. `/anomalies?connection=<retired id>` silently falls back to the seed ("Default") view. Pod names/StatefulSet identity stay stable; Valkey node ids do NOT in this setup (no persistence: 73 ids for 73 pod incarnations per full run).
11. **Sparse slow commands detected late.** slowCommands: 10.8 s (final run) / 22.7 s (previous run) from the first slowlog entry, vs 0.8–3.3 s for every other fault. Cause (corrected): slowlog_last_id uses consecutiveRequired: 1; SLOWLOG is read every 30 s by SlowLogAnalyticsService, so detection waits for the next 30 s read.
12. **Webhooks can't reach in-cluster receivers.** v0.55.0 `apps/api/src/webhooks/webhooks.service.ts` `createWebhook` → `assertSafeOutboundUrl(dto.url, { label: 'webhook URL', resolveDns: 'production' })` (`apps/api/src/common/utils/outbound-url-guard.ts`): private IPs / names resolving to private IPs rejected when `NODE_ENV=production`; `allowPrivateNetworks` exists in the guard but webhooks never pass it, and no env var enables it. In-cluster receivers (`http://svc.ns.svc.cluster.local`) are therefore impossible in the production image.
13. **Helm chart lags the app and lacks nodePort.** Published chart `betterdb/betterdb-monitor` 0.51.1 (appVersion 0.51.1) while the app was 0.55.0 (tag override needed). `charts/betterdb-monitor/templates/service.yaml` renders `type` and `port` only; no `nodePort`, no `annotations`, no `loadBalancerSourceRanges`.

Positive control: PR #651 (headless-Service seed) held through every roll and kill — 36/36 children registered, zero register/retire churn over 5 min, coverage reasons all `no_targets`.
